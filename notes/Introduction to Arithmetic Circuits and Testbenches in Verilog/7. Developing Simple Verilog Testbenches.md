# Behavioral Testbenches
When you run *behavioral testbenches*, you are essentially testing the behavior of your module. Here, ypu have a **unit under test** (or `uut`) which is the module you are testing. First, you attach a **test vector**, which can be seen as the inputs of your `uut`. With them, you expect some outputs from your *uut*, in which you monitor them. At the end, you have to analyze if the I/O behave accordingly of what's expected.

# Creating Testbenches
A good practice when creating testbenches is naming them according to the module you are testing, adding a `tb` at the end. This indicates that the `.v` corresponds to a testbench and not a source file. Usually, the skeleton of a testbench is as follows:

```verilog
`timescale 1ns / 1ps

module module_tb; // usually does not have I/O

	/* 1) Declare local reg and wire identifiers */
	
	/* 2) Instantiate the module under test */
	
	/* 3) Specify a stopwatch to stop the simulation */
	
	/* 4) Generate stimuli, using initial and always */
	
	/* 5) Display the output response (text or graphics (or both)) */
	
endmodule
```

For example, we can elaborate a testbench for the `adder_substractor` module from [[4. Signed Numbers & Arithmetic Overflow]].
```verilog
`timescale 1ns / 1ps

module adder_substractor_tb;

	/* 1) Declare local reg and wire identifiers */
	parameter N=4;
	// reg for inputs
	reg [N-1:0] x;
	reg [N-1:0] y;
	reg add_n;
	// wire for outputs
	wire [N-1:0] s;
	wire c_out;
	wire overflow;
	
	/* 2) Instantiate the module under test */
	adder_substractor #(.N(N)) uut (
		.x(x),
		.y(y),
		.add_n(add_n),
		.s(s),
		.c_out(c_out),
		.overflow(overflow)
	);
	
	/* 3) Specify a stopwatch to stop the simulation */
	
	/* 4) Generate stimuli, using initial and always */
	
	/* 5) Display the output response (text or graphics (or both)) */

endmodule
```
